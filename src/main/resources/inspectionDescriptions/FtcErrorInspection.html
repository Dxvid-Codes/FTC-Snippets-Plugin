Reports common FIRST Tech Challenge mistakes in OpMode classes and offers quick fixes for them.

The inspection only runs on classes that extend OpMode or LinearOpMode, or that carry a @TeleOp or @Autonomous annotation.

What it reports

  • Missing registration annotation — an OpMode without @TeleOp or @Autonomous never appears in the Driver Station list, which looks exactly like a deploy that silently failed.
  • Missing waitForStart() — the routine runs before the match starts.
  • Missing telemetry.update() — data added with telemetry.addData() never reaches the Driver Station.
  • Uninitialized hardware — a motor, servo or sensor field that is never pulled out of the hardwareMap, which throws a NullPointerException the first time it is used.
  • Thread.sleep() in an OpMode — it ignores the stop button, so the robot keeps moving after the match ends. LinearOpMode.sleep() is interrupt aware.
  • Loop without opModeIsActive() — a while loop in runOpMode() that never checks whether the match is still running.
  • Out of range power or position — setPower() outside [-1, 1] or setPosition() outside [0, 1] is silently clipped.

Example


public class MyAuto extends LinearOpMode {
    DcMotor leftMotor;               // never initialized -> NullPointerException

    public void runOpMode() {
        while (true) {               // never stops when the match does
            leftMotor.setPower(1.5); // clipped to 1.0
        }
    }
}
